# TestApiBrainyGo

Учебный проект с автоматизированными API-тестами сервиса BrainyGo. Проект показывает
работу с `pytest`, HTTP API, фикстурами, зависимыми тестовыми данными и безопасным
удалением созданных ресурсов.

## Что проверяется

- создание и получение пользователей;
- создание и получение корпораций;
- создание и получение пунктов назначения и маршрутов;
- создание корабля и рейса, получение рейсов корпорации;
- корректная работа общего HTTP-клиента, включая query-параметры, таймауты и PATCH.

## Требования

- Python 3.10 или новее;
- доступ к тестовому стенду BrainyGo;
- URL и, при необходимости, данные Basic Auth.
- как минимум один заранее созданный тип корабля на тестовом стенде.

## Установка

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

## Конфигурация

Секреты не хранятся в репозитории. Перед запуском live-тестов задайте переменные
окружения, используя `.env.example` как образец:

```powershell
$env:BRAINYGO_BASE_URL = "https://your-test-api.example.com"
$env:BRAINYGO_USERNAME = "your_username"
$env:BRAINYGO_PASSWORD = "your_password"
$env:BRAINYGO_REQUEST_TIMEOUT = "10"
```

`BRAINYGO_USERNAME` и `BRAINYGO_PASSWORD` можно не задавать, если стенд не использует
Basic Auth. При использовании Basic Auth клиент требует HTTPS. URL должен быть без
пути конкретного endpoint.

## Запуск

```powershell
# Все тесты. Без BRAINYGO_BASE_URL live-тесты будут пропущены,
# а быстрые unit-тесты HTTP-клиента всё равно выполнятся.
python -m pytest

# Только тесты, которые обращаются к реальному API
python -m pytest -m integration

# Только локальные unit-тесты
python -m pytest -m "not integration"
```

Логи интеграционных тестов создаются в `logs/` и не попадают в Git.

## Структура

```text
API/       HTTP-клиент и классы endpoint-ов
Tests/     unit- и интеграционные тесты, pytest-фикстуры
Utils/     конфигурация и логирование
```

## Особенности реализации

- общий `BaseAPI` использует `requests.Session`, единый таймаут и явную конфигурацию;
- тестовые сущности получают уникальные имена, поэтому параллельные запуски реже
  конфликтуют;
- финализаторы регистрируются сразу после создания каждого ресурса, поэтому уже
  созданные данные удаляются даже при ошибке следующего шага setup;
- неуспешное удаление считается ошибкой teardown и не маскируется сообщением в логе.

> Интеграционные тесты зависят от доступности учебного стенда и его актуального API-
> контракта. CI по умолчанию запускает детерминированные unit-тесты без секретов.
